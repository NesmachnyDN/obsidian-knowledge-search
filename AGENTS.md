# Agent instructions

## Authority and scope
Read this file, docs/SPEC.md, docs/ARCHITECTURE.md, docs/ROADMAP.md, applicable ADRs and the nearest component instructions before making changes. The specification defines observable outcomes, ADRs establish decisions, and the roadmap defines dependency-ordered slices. Do not use conversation memory as project authority.

- Default to one bounded, traceable change per PR; the only exception is an **explicitly maintainer-authorized aggregated phase candidate**, composed of separately scoped and tested commits and reviewed once before a single merge. The integration branch is `develop`; `main` is stable release history. Use short-lived branches and PRs into `develop`. Follow [the SDD delivery workflow](docs/development/SDD.md). Inspect current head, working tree, open PRs and actual writers before editing. Preserve unrelated work.
- Start with the earliest admissible roadmap slice. If scope or a decision is inconsistent, reconcile controlling documents before implementation. Standard PHASE_RUN uses bounded PRs reviewed and merged in order. **Only when the maintainer explicitly authorizes aggregated phase review**, record the exception in SDD and a single phase candidate PR: keep independently testable, traceable slice commits and contracts, but do not merge any slice to develop until one final independent full-diff review of the aggregate exact HEAD. A failed gate blocks the entire phase merge.
- Use existing library mechanisms and narrowly scoped, license-reviewed reusable code. Never clone an obsolete application wholesale, require its runtime or introduce parallel implementations without a measured reason.
- Separate UI/Obsidian adapter, pure contracts, document processing, index persistence, retrieval policy and model runtime. No model inference or parsing on the UI thread.
- Prefer small, typed, cohesive functions and modules. Keep dependency direction explicit, no production imports from tests, and no broad cleanup or unrequested refactors.
- Test observable behavior, including failures and recovery. Do not claim a passed test or benchmark without actual evidence. Do not silently substitute hash vectors, truncate input, omit files or downgrade to lexical search.
- At each slice report base SHA, changed files, requirement IDs, tests actually run, evidence, limitations, risks, and readiness for independent review. Merge only within the maintainer-authorized task or phase, after independent review and applicable checks pass; no separate routine approval is required when the task includes delivery. No force push.
- Independent review is mandatory but reviewer-tool-neutral. Codex is never a required reviewer: a fresh, separate ChatGPT conversation using Remote Desktop Commander on the ZenBook is an eligible independent reviewer, including for changes authored in another ChatGPT conversation. Review the complete pinned diff and record exact base/head, evidence, blockers and APPROVE or REQUEST CHANGES in the PR. Changing tools or roles inside the authoring chat, a green CI result or an author self-check does not meet this gate. See SDD for handoff and reviewer separation.
- Respect SECURITY.md. Public repository, PR, CI, logs, issues and artifacts must not contain private source material, credentials, private paths, real vault content or indexes. Use generated fixtures and sanitized aggregate evidence only. Check license/provenance before copying any prior code. Do not transmit vault contents to a cloud provider.
- Read a target Vault's own instructions before touching it. No production vault writes, plugin replacement, heavy inference/indexing, or model downloads without explicit authorization and resource preflight. Use an isolated synthetic vault first.

Development baseline: Linux desktop, CPU-first; other hosts are not claimed supported. Avoid infrastructure that needs separate manual administration. Keep public documentation in English. User-facing orchestration can be in the maintainer's language.
