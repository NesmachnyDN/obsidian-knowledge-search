# ADR-0008 — Host-private, plugin-managed transactional Standalone index

**Status:** Proposed (pending independent OKS-04A full-diff review). **Decision owner:** OKS maintainers. **Supersedes:** no accepted prior Standalone-native storage decision; ADR-0003's Python SQLite experiment is retained unchanged.

## Decision and security boundary

For the **Linux desktop Standalone profile**, keep the bounded, versioned, disposable Markdown lexical index under the local user's private durable application-data location:

```text
$XDG_DATA_HOME/obsidian-knowledge-search/plugins/<plugin-id>/<vault-root-digest>/index/
```

When `XDG_DATA_HOME` is missing or relative, use `~/.local/share` per the XDG convention. This is **not** inside the Obsidian Vault and is not included in the plugin bundle or the Obsidian Sync Vault configuration by default. A source Vault rooted at/above this cache path is rejected; the product never writes original Markdown. Every plugin installation requires only Obsidian + the packaged JavaScript bundle. No SQLite service, Python, binary runtime, model, Docker, internet or user-created filesystem configuration is needed.

The canonical `rootId` is SHA-256 over the real root path, device and inode. Stored `rootId`, schema version, lexical index ID, `sourceVersionSet`, `generationId`, `publishedAt` and hashed generation bytes are checked on open. A moved/replaced Vault intentionally gets a new storage partition and a rebuild. Unknown/foreign indexes fail closed; no automatic destructive recovery.

A generation is an immutable size-capped JSON file with canonical source versions and original-line locators. Commit stages each file with `O_EXCL`, `O_NOFOLLOW` and mode 0600, `fsync`s content, atomically renames it into place and `fsync`s the directory. Publication is the atomic replacement of `CURRENT`; `PREVIOUS` remains the recovery pointer. Cancellation is checked again after the staged CURRENT pointer is written and fsynced, immediately before starting its atomic rename. A requested cancel **before** this checkpoint vetoes publication; after the rename has started, publication cannot be revoked safely, so cancellation is reported as deferred (not as a successful cancellation), finishes the committed generation, and pauses subsequent indexing. A canceled, crashed or failed *pre-publication* stage never becomes a published generation. The successful CURRENT rename is also the synchronous in-memory publication point, before any awaited directory sync or garbage collection. If a post-rename directory fsync fails, the current generation is visible in memory but its power-loss durability is explicitly uncertain (`INDEX_DURABILITY_UNCERTAIN`); preserve PREVIOUS and skip GC. Cleanup failures after a fully synced commit (`INDEX_GC_FAILED`) are reported as degraded maintenance, **not** as a rolled-back or canceled commit. The engine separately exposes `maintenanceWarning`, including when a concurrent cancellation is reported as `CANCEL_DEFERRED`. A rejected `rename(CURRENT)` Promise is *not* evidence that rename did not occur: the store reopens and authenticates the actual `CURRENT` pointer, referenced generation and expected durable `INFLIGHT_PREVIOUS` rollback pointer. An authenticated new pointer is adopted by store and engine with `INDEX_DURABILITY_UNCERTAIN` and an explicit `rename-authenticated-after-error` publication outcome (distinct from `rename-confirmed`); an authenticated unchanged old pointer means the write failed without publication; any corrupt, mismatched or unreadable pointer fails closed with `INDEX_PUBLICATION_UNCERTAIN`, clears engine search visibility and inhibits further commits on that store instance until a new authenticated open. This disambiguation executes under the same deferred-cancellation publication boundary, including during unload. A confirmed post-rename directory fsync error is separately marked durability-uncertain; a later GC error remains `INDEX_GC_FAILED`. No power-loss durability is promised for either uncertain case. Unreachable derived generation files remain subject to the bounded admission quota and are reclaimed after a later successful publication. On recovery from a valid PREVIOUS, the recovered pointer becomes the active snapshot and is preserved as PREVIOUS on the next commit. Startup reconciliation repairs a corrupt CURRENT even if the recovered source versions are unchanged. On startup, recover from a fully authenticated `CURRENT`, otherwise the fsynced `INFLIGHT_PREVIOUS`, otherwise the last compatible `PREVIOUS`; a corrupt referenced generation never becomes searchable. No partial generation is ever advertised as ready. Recoverable `.stage-UUID` files older than 60 seconds are cleaned conservatively; more than eight unresolved stages cause a bounded fail-closed error. Known unreachable generation files are garbage-collected only after successful publication. All cleanup targets are known derived filenames; never traverse or remove source notes.

### B7/B8 failure-ordering clarification (remediation candidate)

**Fail-closed evidence revocation (B7).** A lexical request pins an immutable generation for an ordinary concurrent A-to-B publication, but that snapshot is **not** permission to reveal evidence after an unauthenticated publication. Every in-flight request checks the live storage uncertainty flag (including the short interval before the engine's commit failure handler runs), the engine's current generation and unload state after awaits and immediately before returning its response. A revoked request returns `failed`, zero EvidenceHits, `executedMode: none`, and a null generation ID, with `INDEX_PUBLICATION_UNCERTAIN` or `LIFECYCLE_INVALID`. The original source remains unchanged.

**Three-pointer crash window (B8).** `PREVIOUS` always retains the previous *completed* publication until `CURRENT` switches, rather than being overwritten in preparation for an unsuccessful next publication. Before a new `CURRENT` rename, `INFLIGHT_PREVIOUS` is independently staged, fsynced and atomically published with the authenticated old `CURRENT` pointer. For the first replacement, an empty `PREVIOUS` is seeded with the same valid old pointer (no earlier generation exists). The new `CURRENT` is then atomically published and promoted to memory; **only after that** is `PREVIOUS` advanced to the predecessor. If this finalization fails, the engine exposes `INDEX_DURABILITY_UNCERTAIN` and skips GC, while the independently durable in-flight pointer still protects the predecessor. On restart, recovery tries authenticated `CURRENT` first, `INFLIGHT_PREVIOUS` second, `PREVIOUS` third. An aborted rename leaves the old `CURRENT` and original `PREVIOUS` untouched, even if the in-flight pointer has been updated.

Before advancing the rollback, a commit re-authenticates the predecessor's on-disk immutable generation; a damaged predecessor fails the commit without erasing the last valid older fallback. Before replacing `INFLIGHT_PREVIOUS` for a later attempt, the store checks whether an earlier published generation left a different predecessor in that slot (for example, due to an unsuccessful `PREVIOUS` finalization) and repairs the authenticated `PREVIOUS` first. If repair fails, no new `CURRENT` publication begins. Re-publishing the **same** authenticated generation solely to repair a damaged `CURRENT` pointer does not advance the logical version: the already-authenticated older rollback pointer survives, and GC is not permitted to remove its generation. On open, the store authenticates and retains this predecessor independently of the recovered generation. GC must retain generations named by all three durable pointers; the in-flight slot is derived-only metadata, bounded and outside the Vault. The process is intended for a single writer under the documented local Linux filesystem fsync/rename assumptions, not as a guarantee against hostile concurrent external filesystem mutations. Fault-injection tests cover A→B→rejected C, cancel before C, corruption of B, failure of post-C `PREVIOUS` finalization, subsequent failed D and repeated recovery.


Reconciliation is one in-process, bounded and cancellable generation writer with cooperative scheduling. Actual Markdown parsing is performed by a bundled browser Web Worker (not Node `worker_threads`; rejected by the tested Electron runtime), with one outstanding document, a 5-second timeout and worker termination on failure/unload. Source enumeration is through public Obsidian Vault APIs; bounded descriptor-backed reads from the verified root (64 KiB/source) use no-follow and identity checks to avoid stale cache and unbounded `Vault.readBinary` allocations. The index is revalidated against current source bytes before any evidence is shown. Missed events are additionally detected independently of lexical hits. On **every search**, the engine checks the authoritative Obsidian Markdown path enumeration (at most 512 entries) and bounded, non-content filesystem version hints (regular-file dev/inode/size/nanosecond mtime+ctime, batched up to 16 stat operations). Any discrepancy, even with zero search candidates, returns `degraded`/`RECONCILING` and schedules a single cancellable cooperative authoritative audit. Audits rehash all bounded sources and reparse only changed bytes before atomically publishing; search evidence is always independently rehashed, with its response and all hits pinned to one immutable generation snapshot. In addition, a full SHA-256 audit is triggered by the first **search** after 30 seconds since the last successful audit, even when metadata hints look unchanged. There is **no periodic timer** or unattended infinite scanner: when idle, no checks run. With active queries, ordinary filesystem changes visible in the authoritative enumeration/metadata are detected on the next query, and metadata-invisible changes on the first query after the 30-second bound, plus the bounded asynchronous audit duration. A query during drift/audit or after its generation changes is degraded, not falsely current. Before this bound or with no queries, `ready` means last successfully reconciled snapshot, *not* instantaneous omniscience of unsignaled edits. If the Obsidian enumeration itself omits an undiscovered source, no separate raw filesystem walk is performed; completeness is conditional on the Vault enumeration exposing the source. Maximum scan work is 512 × 64 KiB (32 MiB) in bounded reads, a single writer, cooperative per-source yields and browser-Worker parsing. Large Vaults above admission limits fail explicitly rather than silently truncate. Missed file events still trigger lazy repair after stale-hit suppression. No graph traversal or inferred source coordinates.

## Alternatives considered

| Candidate | Assessment | Decision |
|---|---|---|
| **IndexedDB** | Real transactions, but renderer origin/profile, storage eviction, quota, multi-Vault isolation and app-profile backup/portability need a dedicated Obsidian test. Global renderer storage may combine unrelated Vaults. | Defer; not selected solely for API convenience |
| **`Plugin.saveData()/data.json`** | Supported for small settings, not a proven atomic/persistent multi-megabyte index with generation rollback. In-Vault settings may be synchronized. | Reject for index |
| **In-Vault plugin-owned files (`.obsidian/plugins/…`)** | Easy packaging, but the file content contains original excerpts and typed Properties and may be included in optional Obsidian Sync of community-plugin config/data. | Reject as default on privacy grounds |
| **Host-private XDG plugin-owned files** | No extra dependency, Linux fsync/rename, explicit quotas/recovery, no default Vault Sync transport; can be tested with a disposable host profile. | **Choose for OKS-04A** |
| **SQLite native binding/server** | SQLite Python reference is valid for optional advanced backend, but does not provide a built-in browser/Obsidian-native runtime without bundling a binary or server. | Reject in Standalone |

## Guarantees, limits and evidence

- Bounded: 512 Markdown sources, 64 KiB source bytes, 32,768 source blocks, 16 MiB generation, 50 hits, 512 query bytes, 32 predicates and one active reconciliation job. Refusal and degraded status replace silent truncation.
- Current and previous generations are kept. The hard admission limit is four named generation files (two committed/previous and up to two orphan crash candidates) plus capped transient staging; eight stage-orphan files are the fail-closed admission ceiling. A non-silent cache pressure error replaces unlimited accumulation. A total cache quota alarm and user-initiated purge UI belong to OKS-04B.
- The host profile is a trusted single-user desktop running a single Obsidian plugin instance per Vault. Node does not expose a portable `openat2`-style pinned path walk; checks mitigate but do not prove security against a hostile, continuously renaming *external* filesystem attacker. Multi-process writers sharing the same cache root are not supported. A plugin-reload or concurrent-instance test is mandatory before acceptance.
- Atomicity and crash-durability claims depend on the local filesystem's rename/fsync semantics. Network filesystems and alternative OS hosts are not within this decision's verified support.
- Freshness safety is independent of event delivery: every displayed candidate must pass a new authoritative SHA-256 check and exact byte/Unicode/line locator verification. An in-flight source mutation may still occur after the last check, which is an unavoidable race absent a filesystem snapshot/locking API; no stale *known* content is ever knowingly returned.
- Host-private cache is not part of Obsidian Sync by default. Users' separate whole-home backup/sync utilities may still copy local application data; this is outside OKS network behavior and must be disclosed in privacy docs.
- The plugin neither starts network services nor transmits source/index data. Diagnostic outputs must not contain original excerpts or private paths.
- Native integration test evidence: Obsidian desktop 1.15.1, isolated synthetic profile/Vault, native source indexing, lexical query with original line, event-driven modification and plugin reload. This is **not** a 04B UI acceptance or product release.
- Initial proof uses single-machine Linux desktop and synthetic fixture. Broader UI/workspace, cross-platform support and public packaging remain separate gates.
