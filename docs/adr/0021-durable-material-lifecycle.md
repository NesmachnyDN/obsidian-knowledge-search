# ADR-0021 — Durable material lifecycle evidence and initial baseline admission

Status: proposed for independent DOCS_ONLY acceptance. Authority: ADR-0019, AC-11-POLICY-02/03, ROADMAP POLICY.2, #79/#78/#105. No change to source write, provider, disclosure or operational permissions.

**Prospective supersession notice:** [ADR-0023](0023-standalone-consumer-reuse.md) removes mandatory intake-time lifecycle/marking admission as a consumer dependency. The design below remains historical authority for its accepted bounded slices; no permission to bypass current runtime checks. Reuse exact original-version, retirement, persistence and recovery protections where they protect current search/processing authority. No writer/import enrollment required by the revised read-only policy.

## Decision

New-material marking needs a lifecycle classification distinct from current-note Properties and external eligibility. Extend the existing host-owned NewMaterialTracker; do not add a competing policy or source authority. Its durable records are evidence of an admitted exact version, not grants. Continue using the canonical protected original reader and shared evaluator. Offline Basic Search must remain usable when the lifecycle subsystem is absent, unavailable or corrupt.

- **Existing** means an exact original admitted to an explicitly confirmed initial baseline, or an exact successor of admitted existing material, or an admitted new material whose separately authorized marking lifecycle has been completed. **Verified-new** means an observed trusted native creation or admitted import, and its verified successors, pending completion. **Unresolved** is every other state. A startup inventory, path, matching content hash, index entry, metadata cache, missing event, caller claim or note Property is never sufficient. Without marking rules, no automatic marking workflow is required; all normal source/policy and consent gates remain in force.
- Initial baseline is an explicit local owner action, not automatic startup discovery or a way to reclassify pending new materials. Preview the bounded candidate set of exact original versions from the verified host, with counts and paths locally, clearly label the existing-material designation and its effect (no new-material automatic marking). Bind exact root, scope, source IDs, version proofs, rule revision, host/session and one-shot confirmation. Exclude already verified-new and event-ambiguous candidates. Revalidate complete candidate set and exact versions before atomic admission; changed selection, root, source event, rules, expiry or owner invalidates the preview. No note modification, external eligibility assertion or disclosure. A partial/over-limit/unverified initial inventory cannot be silently admitted. One initial baseline per trusted lifecycle epoch; no automatic reset/rebaseline on storage failure. Recovery or deliberate migration requires a distinct explicit contract; never recast a pending new item as existing to avoid a rule.
- Keep exact observed root/path/content/version proof (POLICY.2d). After restart, only an authenticated durable record and an exact freshly observed original version may restore a classification. A mismatched or missing record/version is unresolved; no guessed continuity from digest or inode. Within a live session, pin the same verified native owner and a prior admitted version, require a trusted unambiguous transition event plus a new canonical version proof. For a changed version, require separate reader-derived stable descriptor identity evidence (domain-separated opaque ID, root + device/inode/birth identity where supported) in addition to the native owner/event; it does not prove continuity alone. Unsupported identity, same-byte replacement, uncertain events, collisions, folder moves, overflow, ambiguous owner, missed change or failed read denies advancement. Delete/rename/modify and source/rule changes retire affected authority before observers. On restart or missing events do not advance a prior record merely because an identity token matches. Persist only verified transitions; revalidate exact versions at every restoration and policy-use boundary.
- A verified-new record remains pending until a separately authorized local marking operation has completed a current rule decision, including explicit private or no-write result, or a separately admitted writer has verified the resulting exact original. The policy evaluator is read-only and cannot finalize lifecycle as a side effect of retrieval or egress. Record completion with the rule revision; no automatic retroactive rewrite of existing material when rules change. Pending decisions/confirmations/grants are invalidated on rule changes; pending verified-new materials reevaluate current rules. Organizational restrictions and current Properties always apply regardless of lifecycle.
- Trusted import provenance is a later bounded adapter contract: explicit host admission of exact adapter/channel identity and event provenance bound to the exact original version, root and lifecycle transition. Distinguish proven direct/non-import from unknown channel; a self-declared Property or absent provenance is not proof of either. Changes require new verified binding. No import adapter is admitted by this ADR.
- A separately enabled writer is later gated by actual Vault governance and a demonstrated atomic version-bound native update mechanism. A check-then-write susceptible to external concurrent edits is not a sufficient CAS; deny when such a mechanism cannot be proved. Preserve explicit private, use exact pre/post-read proofs, handle failure/uncertain completion without granting eligibility, and never write existing notes en masse.

## Persistence and threat boundary

Keep one bounded versioned host-private per-root provenance ledger under local data storage outside the Vault, never in Vault sync, Git, diagnostics or indexes. Store only source identities, opaque proofs, admitted origin/transition and completion metadata; no note bodies, credentials, consent or grants. Strict schema, canonical ordering, source/count/byte limits, no silent eviction to existing. Store current immutable snapshot and trusted commit identity/anchor, with authenticated binding of schema/root/epoch/revision/parent and exact content. Reject missing, corrupt, modified, foreign, replayed or incompatible snapshots; do not load an older candidate as live authority merely because its checksum is valid. Reconcile only the last demonstrably committed snapshot; uncertain publication fails closed. A trusted current anchor must distinguish a replayed snapshot from the current committed revision. Reuse reviewed descriptor-anchored local IO and atomic publication primitives where suitable; validate no-follow ancestry, owner/mode, links, bounded reads, fsync, atomic commit and cancellation, and close all handles. Serialize one writer per Vault across plugin reload and concurrent host instances with a verified exclusive transaction/lock; no timestamp-only stale-lock takeover. Define crash recovery and stale owner proof before accepting a backend.

The trusted computing base is the authorized host process, OS identity and host-private storage/anchor. Vault content, indexes, arbitrary callers and substituted/stale ledger records are untrusted. A compromised host/OS or attacker able to roll back every trusted anchor and its backing state together is outside this local-only guarantee; do not claim cryptographic anti-rollback against that attacker. Explicitly verify the actual backend's anchor durability, ownership, cross-instance locking and rollback boundary on each claimed platform; if a trustworthy anchor or exclusive recovery cannot be established, leave durable classification unresolved, not permissive. No new required runtime for Gate A; unsupported platforms keep marking unavailable. An isolated synthetic anchor or checksum alone is not production evidence.

Verify exact unchanged recovery, same-byte replacement, rename/delete, missing and out-of-order events, rules change, scope/root change, duplicate/replayed provenance, forged metadata, tamper/rollback/partial write, concurrent writers, crash/restart/unload and zero unauthorized requests/writes.
