# ADR-0006: Obsidian-native Standalone baseline and explicit advanced execution profiles

Status: Accepted architectural baseline — independently reviewed and merged to develop in PR #9 (2026-11-22). Concrete runtime, storage, model packaging and host API selections remain conditional on later measured ADRs.

## Context and supersession

The product owner requires an operational minimum consisting solely of Obsidian and an installed OKS community plugin, with no separately installed/configured/launched interpreter, database server, container, inference host, or network. Earlier ADR-0001 describes a local supervised companion as a design baseline; ADR-0002/0003 prove bounded Python stdio and SQLite prototypes. They do **not** prove installable standalone search. This decision **refines ADR-0001's deployment/runtime assumption**, and supersedes mandatory companion-runtime interpretation in ARCHITECTURE, not the measured prototype findings or their immutable evidence. No existing Python logic is silently relabeled plugin-native.

The current plugin is an explicit *synthetic evidence probe*: `plugin/src/main.ts` configures `Supervisor` with operator-supplied absolute Python and `engine/probe.py` paths. `engine/document.py`, `native_document.py`, `chunking.py`, `lexical.py`, `storage.py`, `resources.py`, and extraction/OCR dependencies form a Linux/Python experimental engine. Node's built-in child_process in the Obsidian desktop renderer does not make Python an included runtime. The existing `dist/` package is not a user-ready search plugin.

## Decision: three explicitly observable profiles

| Profile | Installation and execution | Required behavior | Boundaries |
|---|---|---|---|
| **Standalone** (mandatory, default) | Only Obsidian + installed plugin; plugin-supplied JavaScript/TypeScript bundle, with independently validated optional web-standard/WASM components. No Python, shell invocation, model download, Ollama, Docker, manually configured API, or server. | Offline Markdown lexical retrieval, supported structured Properties predicates, indexed/wiki-link metadata (without mandatory graph traversal), source opening, exact source identity/locator and provenance, local derived index, mutation/rename/delete reconciliation and stale-hit suppression. | The baseline must not use external runtime or network. Not semantic/hybrid unless a **separately validated real** dense engine is actually present and enabled. |
| **Bundled Advanced** (optional) | Plugin-supplied and plugin-managed dependencies/models/worker; **no manual dependency installation**; explicit activation, locally executable, offline after installed provisioned assets. | Advanced formats/OCR/embedding/dense/hybrid only when validated, licensed, resource-bounded, and actually ready. | Model and runtime sizes, integrity, host/API compatibility, process/worker lifecycle and uninstall must be proven. It is not selected by assumption. |
| **External Backend** (optional) | User explicitly configures a separately managed local service/API, with trust boundary and authentication. | Heavy binary parsing/OCR, real embedding/reranking/hybrid when backend is ready and profile is compatible; source text transferred only with explicit, appropriately scoped user consent. | Absent, failed or disabled backend never disables Standalone lexical search. No cloud/document egress by default, no automatic backend discovery or hidden listeners. |

Profile nomenclature is not an algorithm claim. **Lexical** means lexical candidates only; **dense** requires verified model-backed vectors; **hybrid** requires both independently healthy candidate legs and a documented deterministic fusion. `requestedMode`, `executedMode`, enabled capabilities, availability/readiness and per-leg diagnostics must be observable. Requesting dense or hybrid with the required leg missing/incompatible returns a typed `CAPABILITY_UNAVAILABLE`, `MODEL_UNAVAILABLE`, `INDEX_INCOMPATIBLE` or `LEG_FAILED` response and no mislabeled hybrid results. A user may explicitly choose a new lexical search; it is **not** a silent fallback inside the failed request. Disable/teardown of an advanced profile must leave standalone lexical service and its committed records intact.

CAP-04 and CAP-05 remain MVP-wide acceptance requirements in at least one documented, fully measured **local/offline advanced profile**, independent of the baseline lexical capability. An optional External Backend experiment is not evidence that the default installation has hybrid search. MVP cannot be accepted if those capabilities are unavailable in *all* supported profiles. The minimum clean-install acceptance tests are independent and mandatory. CAP-02 full document/OCR criteria are also retained for a separately documented advanced profile; Markdown is the minimum standalone supported source class, with explicit unsupported/partial status for the rest. Do not conflate MVP-wide advanced-gate evidence with Standalone readiness.

## Deployment partitions and canonical data ownership

- **Obsidian adapter:** use public Vault and MetadataCache APIs for file enumeration, link resolution, frontmatter/Properties types, change notifications, scoped opening and navigation. Validate current bytes and version at retrieval, not just eventual metadata events. Index is derived, not authoritative. Node/Electron APIs require desktop-only manifest and verified minimum app version.
- **Standalone core:** a first-class plugin-bundled, bounded and cancelable indexing/retrieval implementation; no parsing, index rebuild or expensive processing on the renderer UI thread. Choose a supported background scheduling or worker mechanism via compatibility PoC. Use safe bounded batches if worker API compatibility is unverified. Do not assume a plugin can launch external executables.
- **Canonical contracts:** document and source identities use normalized vault-relative paths plus content SHA-256 and extraction status; typed Property values distinguish strings, numbers, booleans, dates and multi-valued keys without lossy string coercion. A ParsedBlock has stable order, kind, headings, original text, links and **explicit available or missing** locator. Markdown locators use verified source spans (one-based lines, half-open UTF-8 byte/Unicode character offsets per contract); PDF/DOCX use native item/page/geometry anchors, never invented file-byte offsets. Chunk carries deterministic identity, source version, ordered slices, original vs contextualized embedding text, tokenizer/serialization/policy identity, diagnostics and no silent truncation. EvidenceHit binds source digest, exact excerpt and original locators, leg ranks/scores and capability diagnostics. Evidence never derives its reference from a generated summary. Contextualized text is not original evidence.
- **Cross-runtime parity:** the Python `ParsedDocument` / `SourceSlice` / `SourceLocator` / `Chunk` model is the starting semantic reference, **not** an imported Python dependency for plugin use. Start from [portable contract semantics](../../contracts/portable-model.md); freeze a language-neutral versioned JSON wire contract and canonical fixture set before implementing JS native runtime or backend bridging. Cross-language conformance tests cover Unicode/CRLF, scalar and typed Properties, links, multiple locators, optional/missing anchors, IDs, source hashes, version errors and negative cases; preserve existing v1 probe contract unchanged. Different internal storage engines are permitted only if external evidence semantics and index-generation compatibility are explicitly tested. Do not create competing evidence schemas.
- **Storage and freshness:** the plugin owns an isolated local derived index scoped to the vault and schema/profile; rebuild/uninstall must never delete source content. Standalone local persistence technology remains a **measured choice** (candidate: transactional IndexedDB or plugin-managed bounded storage). Test Obsidian app-profile/vault isolation, migration, transaction durability, quota and crash recovery; `data.json` alone must not be assumed scalable or atomic. No external database. Hybrid publication must make lexical+dense+manifest a consistent generation, or reject incompatible/mixed results. Suppress changed, deleted, inaccessible or uncertain-source hits even if a previous generation still exists.
- **Python disposition:** retain Python extractor, lexical/FTS5, SQLite, chunk planner and host cgroup experiments as a measured **reference engine and eligible opt-in local backend**, not shipped as a mandatory runtime. Keep its historical benchmarks and tokenizer evidence intact. Reuse standardized data contracts and tests rather than porting Docling/OCR or the full Python engine prematurely. Packaging a Python interpreter in the plugin is **not** an approved Bundled Advanced choice; it would need a separate policy, binary/license/size, lifecycle and cross-platform decision.
- **Network and privacy:** no telemetry or external requests on baseline search; no model/file downloads without explicit reviewed provisioning. Backend connection opt-in and disabled by default, authenticated and scoped, no accidental raw-content logging. No source data in public fixtures or hosted CI. The documented provider must not silently transmit to an Internet/cloud endpoint.

## Readiness and transitions

A capability has explicit states `disabled`, `unavailable`, `provisioning`, `initializing`, `ready`, `degraded`, or `failed`; the ready state binds profile, backend/version, content scope, model identity when applicable and committed index generation. Advanced readiness is separate from Standalone readiness. A mode request is validated **before** execution; a failure mid-query returns a typed partial/failure diagnostic with no semantic promotion of an incomplete leg. A degraded lexically valid result is only a *lexical* result if the user initiates an explicit lexical request; error states never masquerade as completed hybrid retrieval.

Activation, pause/cancel, retries, pressure admission and recovery must be bounded. On advanced startup failure, stop that component and preserve the ready standalone generation. On source modification/delete/rename, invalidate affected hit visibility immediately and reconcile asynchronously; missing freshness evidence means suppress hit. Index migration or shutdown must not erase the previous committed generation on failure.

## Experiment and adoption gates

1. **Before OKS-03A:** keep this document-only change separate from an implementation migration. Inspect official Obsidian developer requirements, prove Node/worker/WASM/WebGPU/CPU availability rather than assuming desktop renderer compatibility, and distinguish the current synthetic probe from any production search feature. Record exact host/app/manifest and CI evidence when implementation reaches those gates.
2. **OKS-03A:** compare existing permitted Python CPU reference runtime with Obsidian-executable candidates (browser WebAssembly/ONNX or other licensed WASM runtimes, only if API, model and tokenizer parity can be proven) and a plugin-managed bundled candidate. Check BGE-M3 weights/tokenizer revision and artifact hashes, effective token max and full serialization, special tokens, 1024-dim output, finite/norm vectors, repeatability, no truncation, measured RAM/CPU/latency, offline loading, cancel/pressure recovery, and explicit model-unavailable failure. **No new heavyweight artifact download without separate permission and a budget.** An infeasible bundled candidate is reported, not faked.
3. **OKS-03B:** independent real lexical and dense legs plus deterministic RRF, typed filters, exact identifiers, original anchors and generation freshness; measure frozen corpus quality/latency/CPU/RSS and structural policies with the actual model and identical conditions. No hash/fake vectors in the confirming benchmark. If dense is unavailable, do not claim hybrid phase exit.
4. **OKS-04A:** build plugin-native Standalone Markdown ingestion and durable lexical index plus incremental lifecycle, typed Properties, link metadata, stale-hit gates and cross-runtime evidence conformance. Python worker is not a runtime dependency.
5. **OKS-04B:** wire plugin search UI, source navigation, readiness/status and index controls; add explicit opt-in advanced/backend configuration and disclosed feature matrix. Validate app lifecycle and no background CPU-heavy renderer blocking.
6. **OKS-05:** clean disposable vault with **only Obsidian and the installed release-shaped plugin package**, offline and no Python/Docling/Docker/Ollama/server present or configured. Index two or more authored Markdown notes with nested heading, link, typed Properties and exact ID; filter, search and navigate to verified original line. Modify, rename and delete notes; verify immediate stale-hit suppression, restart persistence, recovery and safe uninstall; inspect no external process, network/document egress or download; record resources, app/plugin versions and installation bytes. Independently demonstrate CAP-02 advanced formats and CAP-04/05 real local offline hybrid in its eligible documented profile. If any required MVP-wide gate fails, do not declare MVP done.

## Alternatives and reasons

- **Python subprocess mandatory for basic search:** rejected; violates standalone installation requirement.
- **Python packaged without evidence:** rejected as default; package size, runtime distribution, security, portability and Community Plugin policy unproven.
- **All computation on UI thread:** rejected; responsiveness and failure isolation.
- **JS lexical baseline with later eligible dense/Bundled Advanced:** selected; satisfies installability without misleading hybrid claims, preserves current experiments and allows evidence-driven model selection.
- **External backend only:** rejected as sole product execution mode; authorized only opt-in.
- **Fake embeddings or implicit lexical fallback:** prohibited: invalidates CAP-04/05 evidence.

## Consequences, unresolved validation

No standalone functionality is implemented by this ADR. The approved architecture creates mandatory downstream JS native indexing and installation tests, while 03A/03B may first validate the experimental Python backend under strict opt-in/no-download controls. Choosing the exact index persistence API, background worker implementation, model distribution policy, and optional backend authentication/IPC remain gated prototype decisions; none is silently finalized here. Obsidian desktop-only `isDesktopOnly`, its official manifest/release layout, disclosure and network policies must be rechecked at packaging time.
