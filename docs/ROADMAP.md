## OKS-06H conversational knowledge access (2026-11-25 product-owner direction)

The generative chat is a target optional user-facing capability, not merely a single-query synthesis API. In settings, configure the generation role independently from embedding and reranking (API endpoint URL, supported adapter, model, private credential reference and connection status/check). Chat provides a direct navigation link to those settings; it never places credentials in URLs. The two explicit modes are **Vault-wide** (the entire eligible searchable Vault, with local retrieval of relevant evidence only) and **Selected materials** (an explicit user-defined subset). Selection is an additional hard restriction, intersected with current indexing, scope, source freshness and disclosure policy; an empty or invalid selection never expands to the Vault. Source-type coverage is limited to independently supported formats, with exclusions visible.

Every turn uses bounded, verified source-backed context, citations and explicit insufficient-evidence behavior. Multi-turn history cannot reintroduce excluded, deleted, superseded or unauthorized sources; scope/provider changes require revalidation and isolation of prior context. The UI shows active scope, provider/model and status; no implicit cloud fallback, external bulk upload or autonomous source edits. Detailed contracts and thresholds must be frozen in 06H.1; implementation reuses existing generation/consent/lifecycle mechanisms, not a parallel provider stack. See CAP-06/07/09/10/11 in [SPEC](SPEC.md) and [API-first ADR](adr/0015-api-first-ai-optional-dense.md). 06H.3 is an additional prerequisite for OKS-07/08 **only when chat is claimed**, on each claimed host/platform; Gate A and standalone search remain independent. Prioritize 06H after its prerequisites, without requiring unrelated 06-series work or interrupting an active delivery slice.

## OKS-06H processing policy rebaseline (2026-11-26 product-owner direction)

Target direction recorded in [#78](https://github.com/NesmachnyDN/obsidian-knowledge-search/issues/78): replace repeated manual per-excerpt classification with a simple configurable note-level external-processing policy, not user RBAC/ACL. The owner expects about 98% of notes to be externally eligible; this is a planning estimate, not measured coverage. Proposed canonical Property `llm_processing`: exact `external` permits eligibility; verified absence may be eligible only under an explicit configured rule (ADR-0023; unknown is denied); exact `private` prohibits external processing and permits trusted internal processing. Malformed/ambiguous values deny external eligibility. Explicit restrictive organizational policies take precedence. External eligibility does not enable an external endpoint, authorize a specific disclosure, or waive provider admission, exact consent, scope, credential binding, budgets or operational acceptance. Until the controlling specification/security/ADR contracts are independently rebaselined and the new policy implemented, the existing stricter runtime policy remains in force.

No silent fallback, automatic split of interactive RAG requests, incompatible embedding-space mixing or second active dense index. Separate design/acceptance required; not a mandatory chat or release dependency.

## OKS-06B scope and ownership (2026-11-24 product-owner direction)

- **Vault is authoritative; graph is a disposable read projection.** OKS indexes existing source-backed cards and links, not a separate canonical entity/assertion store. Mapping is Vault-configurable and versioned; plain wiki-links are navigation edges, not evidence of a semantic predicate. Unmapped/unknown status must not be labeled confirmed. Only explicitly accepted relationships under the Vault's own governance rules may be presented as confirmed; candidate/rejected/superseded or ambiguous relations cannot enter confirmed-only retrieval.
- **No graph confirmation subsystem in OKS.** New entity/relationship discovery, candidate card creation, deduplication, conflict resolution and expert confirmation belong to the existing Vault/agent curation workflow, not plugin-owned graph administration. Existing accepted cards/relations need no second confirmation. Optional future AI-assisted extraction or dependency/conflict analysis requires a separate maintainer-approved scope and contract; this roadmap does not authorize an extraction service, autonomous source edits, a new ontology or a review UI.
- **Minimal user surface:** existing search UI/API/CLI with an optional related-knowledge expansion setting, truthful confirmed-status filtering where configured, and source-backed relation/path explanations. No separate graph editor, node/edge review dashboard or custom visualization required. A missing/unready graph cannot disable basic search; a requested graph mode must not silently report successful expansion if it did not run.
- **Security and lifecycle:** graph artifacts stay host-private, disposable and rebuildable; never sync/export them by default or disclose unauthorized intermediate nodes, edges, source text or path explanations. Reuse canonical source/evidence verification and existing egress controls. No provider requests for deterministic graph construction/traversal. Do not introduce a second dense space, mandatory AI/runtime or a graph database. Retain the original Gate A/B/C partition, and do not expand the active 05P implementation or claim graph acceptance before independent review and 06B.4 evidence.

## OKS-06F product-owner direction (2026-11-25)

Core-first single-plugin onboarding, contextual one-action optional document runtime and Linux/Windows/macOS/Android/iOS/iPadOS portability are agreed target requirements, not delivered capabilities. Android tablet is the first mobile target; 06F.1 is the design prerequisite, and 06F.4 need not wait for Windows/macOS or desktop runtime packaging. Preserve existing feature gates; platform claims require exact-platform acceptance. Community Directory policy forbids self/dependency installation by plugins: compliant external provisioning is a design/release gate, not a waiver. No automatic downloads merely on startup or detection of documents. See [ADR-0016](adr/0016-platform-portability-managed-runtime.md).

## OKS-06G product-owner direction (2026-11-25)

The full document profile requires searchable attachment contents in MD, TXT, PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, VSDX, drawio, PNG/JPG/JPEG/BMP, Mermaid/UML and MSG, without custom preview. Extend via reviewed format adapters, not separate search stacks. Prioritize 06G.1 alongside 06F.1 so runtime packaging selects dependencies once; 06D cache contracts must accommodate generic extractors. No expanded format claim without the matching Gate C; adoption of the full document profile in 07 requires 06G.5. Existing basic-only release remains independent. See [ADR-0017](adr/0017-extensible-multiformat-extraction.md).
