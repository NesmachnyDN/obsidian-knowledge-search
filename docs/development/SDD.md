# Spec-driven delivery (SDD)

## Authority

The chain is Specification (CAP/AC) -> Architecture / accepted ADR -> dependency-ordered Roadmap -> bounded execution contract -> implementation and tests -> independent review -> authorized merge. GitHub issues, PRs, commits and check results are the sole execution-state history; do not maintain duplicate state ledgers. A candidate issue is not implementation authority until relevant requirements and roadmap are reconciled. Prefer the smallest complete change and use existing SDKs, standard libraries or maintained dependencies before custom mechanics.

## Branches and authorization

- `develop` is the integration branch. By default each bounded task uses one short-lived branch and one PR into develop; an **explicitly authorized aggregated PHASE_RUN** instead uses one phase branch/PR with individually auditable slice commits and a single final review/merge. `main` is stable release history; release promotion is a separate maintainer decision.
- The maintainer's assignment of an implementation task under this delivery workflow authorizes ordinary edits, tests, branch/commit/push, PR creation, within-scope remediation, and merge into develop **only when all gates below pass**. An explicitly planning-only, review-only or no-merge assignment overrides this default. Authorization does not extend to unrelated changes, releases or privacy/operational exceptions.
- `BOUNDED_SLICE` is the default for a named task. Standard `PHASE_RUN` continues successive eligible bounded PRs with exact-HEAD independent review and merge at each step. **Aggregated PHASE_RUN is an explicit maintainer-authorized exception:** a single Draft phase candidate PR against a pinned develop base contains individually traceable, tested slice commits/contracts (not unrelated features). Complete the phase before one final independent full-diff review of the entire phase HEAD, then run all CI/acceptance gates and merge the aggregate once. No intermediate merge, draft-to-ready transition, or self-approval. If develop changes, refresh base/validation and independent review before merge. The exception must be recorded in its phase contract and PR; it does not relax security, model permissions, benchmark acceptance, review separation or future default SDD.
- Do not bypass branch protection, force push, overwrite unrelated work, approve your own implementation, or merge when a required check or independent review is absent. No automatic transition of main.

## Standard cycle

1. **Intake and freshness.** Fetch remote develop, record exact base SHA, review relevant open PRs/issues, dependency merge status, working tree, active writers and resource conditions. Reuse unfinished eligible work. Keep unrelated work intact. If a task changes product scope, accepted architecture or an acceptance criterion, resolve the upstream document change before code.
2. **Bounded contract.** The orchestrator selects an eligible roadmap slice and writes an English execution prompt under `docs/prompts/` (or a versioned PR/issue contract for minor fixes). Include task, base SHA, CAP/AC references, ADR/roadmap and exact applicable sections, in/out of scope, dependency/reuse decision, affected components, positive and negative tests, resource/privacy constraints and measurable exit. No parallel contracts for the same task. Documentation-only work may be performed directly.
3. **Implementation.** ChatGPT owns architecture and orchestration; Codex CLI is the preferred bounded implementation worker, not a required dependency. If Codex is unavailable, an authorized ChatGPT implementation session may work on the Linux test host through Remote Desktop Commander and local tools, with the same scope, test and safety requirements. Read root/path-local instructions, resolved execution contract and relevant code. In local orchestrated mode a worker edits and runs cheap checks; the orchestrator runs larger validation, inspects the diff and handles delivery. When explicitly delegated, Codex may commit/push/open a draft PR, but cannot act as its own independent reviewer or merge. No broad refactor, extra dependency or duplicate algorithm outside scope. Preserve a recoverable branch on interruption.
4. **Validation and PR.** Run applicable focused tests, build/type/lint checks and failure-path tests; record commands, observed results and unavailable or inapplicable checks. Push normally and open/update a draft PR with exact base/head, requirement traceability, privacy and operational impact. No synthetic claims of runtime or benchmark success. For explicitly authorized **aggregated PHASE_RUN**, keep one phase Draft PR, create separate scoped commits per slice, validate and document each checkpoint, and extend that same PR for the next slice. Retain its original base; final review compares the **entire phase diff**, not just the last commit.
5. **Independent review (tool-neutral hard gate).** A reviewer who has not authored or remediated the candidate must independently inspect the **complete diff at the exact candidate HEAD** against the current recorded base. In explicitly authorized **aggregated PHASE_RUN**, perform this independent full-diff review **once after all in-scope phase slices are implemented and measured, but before any phase change is merged to develop**; the entire phase is one candidate and one review gate, rather than author-only acceptance of intermediate commits. New changes after approval require a new full-diff review of the updated HEAD. Eligible reviewers are: (a) ChatGPT in a **new, separate conversation** using Remote Desktop Commander to examine the actual Linux test host repository; (b) a distinct Codex reviewer session when available; or (c) an independent human reviewer. These modes are interchangeable for the SDD gate regardless of whether the implementation or subsequent fixes were written by Codex or ChatGPT. A switch of tool, model or reviewer persona **within the same authoring conversation** is not independent review. Codex availability or quota is never itself an approval requirement. The reviewer reads the actual governing files and full diff rather than trusting author assertions or CI, and checks scope/requirements, architecture, correctness, negative tests, security/privacy, dependencies/licenses, source provenance, resource bounds and recovery. Record exact base SHA and head SHA, reviewer mode, relevant tests/evidence, findings with file/line references, blockers versus warnings, and explicit **APPROVE** or **REQUEST CHANGES**. Publish a sanitized report on the PR; when a separate ChatGPT chat uses the maintainer's GitHub account, a PR comment is valid process evidence of its *session-independent* review, but must not be misrepresented as a GitHub platform approval by a different account. No test exit code, green CI, written summary from the author or self-check substitutes for review. The reviewer does not modify the reviewed candidate or approve their own fixes: blocking changes go back to the implementation role and any changed HEAD requires a fresh independent review. Do not merge with unresolved mandatory blockers.
6. **Completion.** Verify exact remote head, current develop and mergeability; required CI/checks passed for that head, required manual/evaluation evidence recorded, no unresolved blocking review threads/findings. Change draft to ready and merge the authorized PR into develop (prefer squash merge; no force). Verify actual merged status and develop SHA; update directly related issues and report the result. If develop changes materially, synchronize, revalidate and review before merge. Do not bypass CI failures. Missing CI is acceptable only for documentation-only bootstrap when no required check exists and the actual documentation checks and independent review are recorded.
7. **Continue or close.** For standard PHASE_RUN select the next admissible slice from refreshed develop; for **aggregated PHASE_RUN**, select the next dependent bounded slice on the unmerged phase branch after checking its independently measured entry gates, then close only after the aggregate PR is reviewed and merged. For BOUNDED_SLICE stop at merged verification. Do not launch detached unattended development or promise future completion; interrupted work stays recoverable and its actual status must be reported. Track follow-up opportunities as scoped GitHub issues, not hidden expansion.

## Separate-chat review handoff

If Codex is exhausted, unavailable or unsuitable, do not retry it as a mandatory reviewer. The implementing chat prepares an exact-head handoff containing the repository/PR URL, base and head SHA, applicable AGENTS/SDD/contract, changed paths, relevant validation results, known limitations and unresolved findings **without presenting its own review as approval**. The maintainer opens a **new ChatGPT chat** and instructs it to use Remote Desktop Commander on the Linux test host for read-only, full-diff review; a fresh chat cannot be created or simulated by changing the role in the implementation chat.

The separate reviewer must independently fetch and verify GitHub base/head/CI and local Git/worktree status, read governing documents and the complete diff, inspect risk-bearing code and tests, and provide a file/line-grounded APPROVE or REQUEST CHANGES **for that exact HEAD**. It records the sanitized conclusion in the PR. On REQUEST CHANGES, return findings to the implementing chat for remediation, then request an independent review of the **new** HEAD. On APPROVE, the authorized orchestrator may continue the normal readiness, CI and merge gates; the reviewer's approval never bypasses them. If no separate reviewer is available yet, leave the PR open and unmerged with a recoverable handoff; do not claim completion.

## Documentation and issue fast path

Maintainer decision (2026-11-25): use the standing `DOCS_ONLY` and `ISSUE_ONLY` profiles below instead of full functional acceptance for documentation and backlog maintenance. No separate authorization is needed to select an eligible profile within an authorized task. This section specializes the standard cycle and completion requirements for these profiles only.

- **ISSUE_ONLY:** Creating or updating GitHub planning issues requires only a proportionate check for duplicates, scope, relevant requirements/roadmap, dependencies, confidentiality and accurate status. Verify the resulting issue URL and content. No repository changes, branch, PR, merge, independent code review, build or test run is needed. An issue is not implementation authority or evidence of delivered functionality.
- **DOCS_ONLY eligibility:** The complete diff must contain only non-executable documentation or planning material, such as Markdown specifications, ADRs, roadmap, prompts and development instructions. Confirm the actual content and file types, not just extensions or directory names. Changes to source, executable scripts/configuration, dependencies, CI/CD, generated runtime assets or mixed code/documentation changes are ineligible. A documentation change may define future requirements or architecture only with the necessary maintainer decision and consistency/traceability checks; it cannot certify implementation, waive existing product/security gates or retroactively claim acceptance.
- **DOCS_ONLY cycle:** Reconcile current develop and exact candidate HEAD; inspect the complete diff, validate scope, document consistency/authority, affected references, Markdown/links and whitespace (`git diff --check` or equivalent). Obtain a concise independent exact-HEAD documentation review under the existing reviewer separation rule. Record base/head, changed paths, observed checks, applicable CI, blockers and APPROVE or REQUEST CHANGES in the PR. No expansive code audit or phase-close report is required. For changes to normative requirements, ADRs, security or SDD policy, specifically check the affected authority and gate consistency.
- **DOCS_ONLY merge:** After the focused review and applicable checks pass, verify current base/head, no blockers or unresolved blocking threads, and mergeability; mark Ready and squash merge into develop within the authorized scope. Never bypass required checks or branch protection, or ignore actual CI failures. If no CI is configured or triggered and no check is required, record that fact with the actual documentation validation and independent review. Recheck a changed HEAD before approval/merge. Verify MERGED, resulting develop SHA and the updated documents on develop.
- **Not applicable:** Additional local builds, unit/integration/E2E, full regression, load tests, runtime lifecycle audit, expanded source security audit and re-review of unchanged code are NOT APPLICABLE to a verified DOCS_ONLY candidate unless a specific relevant risk or controlling requirement demands them. Do not launch Codex merely to repeat mechanical checks; it is optional for focused review under the model/quota policy. Existing applicable CI is not skipped. Never report unexecuted checks as PASS.
- Keep the standard SDD cycle, exact-HEAD independent review and all applicable functional acceptance gates for implementation changes. A documentation-only PR is not a phase or release acceptance. If eligibility is uncertain, use the standard profile.

## Quality profiles

- ITERATION (default): exact traceability, focused deterministic tests, build/type/lint checks where applicable, negative failure cases, independent full-diff review, applicable CI, and scope/privacy check.
- PHASE_CLOSE: ITERATION plus milestone-specific integration/regression, reproducible acceptance benchmark and lifecycle/resource/rollback evidence required by the specification and roadmap. Standard workflow retains bounded PRs; an explicitly approved aggregate phase PR still requires bounded auditable slice commits, one independent full-phase review before the sole merge, and **all** exit gates. Phase closure is not implied by an implementation commit or green CI.

## Stop conditions

Stop for an unresolved material architecture/product decision, contradictory authority, changed scope requiring approval, unavailable explicit permission or dependency, unremediable required validation/review/CI failure, confidentiality or licensing risk, or unsafe host condition. A routine test failure, Codex quota exhaustion when a separate ChatGPT review chat is available, a review finding fixable within scope, or a recoverable transport failure is not itself a reason to ask the maintainer to continue. An unavailable independent reviewer *after* allowed handoff attempts remains a merge blocker. Try permitted alternatives without bypassing a specific safety refusal. Do not run heavy inference, downloads, mass indexing, production vault operations or host configuration changes without separate authorization and resource preflight, even within PHASE_RUN.

## Engineering and review standard

Keep UI, protocol, parser, indexing, retrieval and model runtime ownership distinct. Prefer small typed cohesive modules; file size is a review signal rather than an arbitrary split mandate. Require deterministic source identity, explicit failure/partial status, no silent truncation/fallback, bounded queues, safe cancellation, atomic index publication, no production imports from tests or unreviewed copied code. Security and license review are hard gates. For each candidate review report: scope/traceability, architecture, code quality/modularity/reuse, tests/CI, privacy/operations, risks, required changes and final recommendation. Review must cover actual changed behavior and not just documentation claims.

## Codex model and quota policy

Maintainer decision (2026-11-25): use the least expensive adequate Codex model and reasoning tier across all OKS delivery stages, including bounded implementation, review, remediation, re-review and phase acceptance. This governs development tooling only, not plugin runtime AI providers. Check the installed CLI model catalog and supported reasoning levels before selection; catalog presence is not proof of remaining quota or service access.

| Work class | Default model (current CLI catalog) | Reasoning effort |
| --- | --- | --- |
| Routine independent code/SDD review, bounded implementation and remediation | GPT-5.6 Terra (`gpt-5.6-terra`) | `medium` |
| Simple documentation, mechanical checks and small low-risk edits | GPT-5.6 Luna (`gpt-5.6-luna`) | `low` or `medium` |
| Demonstrably difficult unresolved review/implementation question | Terra or GPT-5.6 Sol (`gpt-5.6-sol`) | `medium`; `high` only with a recorded concrete reason |

- Explicitly set the model and reasoning effort for each new Codex invocation; for example, `codex exec -m gpt-5.6-terra -c 'model_reasoning_effort="medium"'` with the existing bounded prompt, sandbox and timeout controls. Do not rely on a potentially expensive implicit default. Record selected model, effort and any escalation in the sanitized handoff/review evidence. If the catalog changes, select an available equivalent economical/balanced model and document the substitution.
- Escalate only when concrete ambiguity, conflicting evidence, or a difficult correctness/security issue exceeds the selected tier. Try a focused deterministic check first. Astra/top-tier models and `xhigh`, `max`, `ultra` (or equivalent maximum/pro modes) require separate maintainer authorization; they are not routine review settings.
- Run cheap deterministic checks with local tools rather than asking Codex to repeat them. Pin the base/head, reuse reproducible evidence, and avoid redundant sessions on unchanged candidates. Do not skip the mandatory exact-HEAD full-diff review after a change. On quota exhaustion, do not repeatedly retry or cycle through models to evade limits; use the eligible separate-chat/human review route.
- The complete independent review, security, CI, adversarial and applicable acceptance gates are unchanged. A smaller model's uncertain or incomplete review is not APPROVE. If an eligible reviewer cannot complete the gate, leave the candidate unmerged. This policy does not authorize production Vault access, cloud egress or host-wide configuration changes.

## Workstation use

Use one active writer per worktree, inspect process state before editing, and avoid parallel heavy work. Codex commands should be bounded, non-interactive with closed stdin, and monitored with explicit time/resource controls. For ChatGPT-authored changes, arrange a new independent ChatGPT chat via Remote Desktop Commander or a distinct Codex/human reviewer; never reuse the authoring conversation as its own reviewer. Review a pinned committed candidate against its explicit base. Do not copy sensitive source into prompts, public artifacts or external services; only synthetic test data. A failed transport is not evidence of a failed Git mutation: check generated state before retrying.
