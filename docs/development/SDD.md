# Spec-driven delivery (SDD)

## Authority

The chain is Specification (CAP/AC) -> Architecture / accepted ADR -> dependency-ordered Roadmap -> bounded execution contract -> implementation and tests -> independent review -> authorized merge. GitHub issues, PRs, commits and check results are the sole execution-state history; do not maintain duplicate state ledgers. A candidate issue is not implementation authority until relevant requirements and roadmap are reconciled. Prefer the smallest complete change and use existing SDKs, standard libraries or maintained dependencies before custom mechanics.

## Branches and authorization

- `develop` is the integration branch. Each bounded task uses one short-lived branch, one PR into develop. `main` is stable release history; release promotion is a separate maintainer decision.
- The maintainer's assignment of an implementation task under this delivery workflow authorizes ordinary edits, tests, branch/commit/push, PR creation, within-scope remediation, and merge into develop **only when all gates below pass**. An explicitly planning-only, review-only or no-merge assignment overrides this default. Authorization does not extend to unrelated changes, releases or privacy/operational exceptions.
- `BOUNDED_SLICE` is the default for a named task. `PHASE_RUN` applies when the maintainer requests a named phase or milestone through completion: continue successive eligible bounded PRs without routine approval checkpoints. Refresh develop, dependencies, open issues/PRs and applicable authorities after each merge. Stop at the phase exit, not at an arbitrary intermediate PR.
- Do not bypass branch protection, force push, overwrite unrelated work, approve your own implementation, or merge when a required check or independent review is absent. No automatic transition of main.

## Standard cycle

1. **Intake and freshness.** Fetch remote develop, record exact base SHA, review relevant open PRs/issues, dependency merge status, working tree, active writers and resource conditions. Reuse unfinished eligible work. Keep unrelated work intact. If a task changes product scope, accepted architecture or an acceptance criterion, resolve the upstream document change before code.
2. **Bounded contract.** The orchestrator selects an eligible roadmap slice and writes an English execution prompt under `docs/prompts/` (or a versioned PR/issue contract for minor fixes). Include task, base SHA, CAP/AC references, ADR/roadmap and exact applicable sections, in/out of scope, dependency/reuse decision, affected components, positive and negative tests, resource/privacy constraints and measurable exit. No parallel contracts for the same task. Documentation-only work may be performed directly.
3. **Implementation.** ChatGPT owns architecture and orchestration; Codex CLI is the default bounded implementation worker. Read root/path-local instructions, resolved execution contract and relevant code. In local orchestrated mode Codex edits and runs cheap checks; the orchestrator runs larger validation, inspects the diff and handles delivery. When explicitly delegated, Codex may commit/push/open a draft PR, but cannot act as its own independent reviewer or merge. No broad refactor, extra dependency or duplicate algorithm outside scope. Preserve a recoverable branch on interruption.
4. **Validation and PR.** Run applicable focused tests, build/type/lint checks and failure-path tests; record commands, observed results and unavailable or inapplicable checks. Push normally and open/update a draft PR with exact base/head, requirement traceability, privacy and operational impact. No synthetic claims of runtime or benchmark success.
5. **Independent review.** A fresh reviewer session (ChatGPT reviewing Codex work, or a separate Codex reviewer for orchestrator-authored changes) inspects the entire candidate diff against its contract, requirements, architecture, engineering quality, reuse, license, tests, privacy, recovery and resource boundaries. Identify blockers with file/line references, distinguish warnings, state APPROVE or REQUEST CHANGES for exact head. A process exit code alone is not review approval. Findings and evidence may be summarized in the PR without private data. Remediate blockers autonomously within authorized scope; rerun affected checks and review the updated head. No self-review substitution.
6. **Completion.** Verify exact remote head, current develop and mergeability; required CI/checks passed for that head, required manual/evaluation evidence recorded, no unresolved blocking review threads/findings. Change draft to ready and merge the authorized PR into develop (prefer squash merge; no force). Verify actual merged status and develop SHA; update directly related issues and report the result. If develop changes materially, synchronize, revalidate and review before merge. Do not bypass CI failures. Missing CI is acceptable only for documentation-only bootstrap when no required check exists and the actual documentation checks and independent review are recorded.
7. **Continue or close.** For PHASE_RUN select the next admissible slice from the refreshed repository; for BOUNDED_SLICE stop at merged verification. Do not launch detached unattended development or promise future completion; interrupted work stays recoverable and its actual status must be reported. Track follow-up opportunities as scoped GitHub issues, not hidden expansion.

## Quality profiles

- ITERATION (default): exact traceability, focused deterministic tests, build/type/lint checks where applicable, negative failure cases, independent full-diff review, applicable CI, and scope/privacy check.
- PHASE_CLOSE: ITERATION plus milestone-specific integration/regression, reproducible acceptance benchmark and lifecycle/resource/rollback evidence required by the specification and roadmap. One bounded PR still owns each selected delta; phase closure is not implied by a merged implementation PR.

## Stop conditions

Stop for an unresolved material architecture/product decision, contradictory authority, changed scope requiring approval, unavailable explicit permission or dependency, unremediable required validation/review/CI failure, confidentiality or licensing risk, or unsafe host condition. A routine test failure, a review finding fixable within scope, or a recoverable transport failure is not itself a reason to ask the maintainer to continue. Try permitted alternatives without bypassing a specific safety refusal. Do not run heavy inference, downloads, mass indexing, production vault operations or host configuration changes without separate authorization and resource preflight, even within PHASE_RUN.

## Engineering and review standard

Keep UI, protocol, parser, indexing, retrieval and model runtime ownership distinct. Prefer small typed cohesive modules; file size is a review signal rather than an arbitrary split mandate. Require deterministic source identity, explicit failure/partial status, no silent truncation/fallback, bounded queues, safe cancellation, atomic index publication, no production imports from tests or unreviewed copied code. Security and license review are hard gates. For each candidate review report: scope/traceability, architecture, code quality/modularity/reuse, tests/CI, privacy/operations, risks, required changes and final recommendation. Review must cover actual changed behavior and not just documentation claims.

## Workstation use

Use one active writer per worktree, inspect process state before editing, and avoid parallel heavy work. Codex commands should be bounded, non-interactive with closed stdin, and monitored with explicit time/resource controls. Use a fresh review session and review a pinned committed candidate against its explicit base. Do not copy sensitive source into prompts, public artifacts or external services; only synthetic test data. A failed transport is not evidence of a failed Git mutation: check generated state before retrying.
