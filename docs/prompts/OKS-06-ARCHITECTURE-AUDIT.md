# OKS-06 — Independent Architecture Scope and Complexity Audit

Authority: AGENTS, SECURITY, SDD, SPEC, ARCHITECTURE, ROADMAP, ADR-0015–0024 and applicable execution contracts. This is an analysis-only checkpoint, not a code review substitute or implementation authorization.

## Objective and independence

Act as Principal Software Engineer, Solution Architect, Product Architect and Security Architect. Determine whether OKS is still a read-only document-processing and retrieval product, rather than a knowledge-management system, and whether current complexity is necessary to deliver the product. Review the merged develop baseline and PR #155 candidate separately. Read ADR-0024 and verify its documentation acceptance state; if pending, distinguish maintainer direction from merged authority. Record exact current SHAs, open PRs, relevant issues, and limitations.

Use authorized repository access, local read-only inspection and isolated synthetic fixtures only. Do not change production code, documents, branches, PR status, issues, or production Vault; no provider calls, secrets, model downloads, deployment or merge. No real private materials in reports or logs.

## Scope and evidence

1. Read controlling documents, applicable local instructions, historical marking contracts, HARD-SCOPE-1–6, prior review findings and author handoffs for PRs #154/#155. Validate the requirements hierarchy and distinguish current policy from superseded prerequisites.
2. Inventory actual modules, owners, storage, dependencies, APIs and paths across host/UI, source reading, extraction, chunking, indexes, retrieval, graph, scoped chat/history, AI adapters, policy and lifecycle. Map each to CAP/AC, user-visible outcome and mandatory/conditional gate. Identify source writes or mandatory producer/curation dependencies, if any. Map Basic dependencies separately from optional profiles.
3. Trace end-to-end Markdown occurrence/Properties search, local attachment extraction/content search, and scoped lexical RAG through actual call paths. Show current implementation, actual evidence, missing integration and independently accepted versus synthetic-only status. Distinguish optional dense/hybrid/rerank, graph and portable artifacts.
4. Assess SearchController and engine/reader authority boundaries, including source identity, operation ownership, publication, role-local retirement, cancellation and pending settlement. Inventory state, owners, aliases, queues, callbacks and transitions. Explain repeated findings in PRs #154/#155 as systemic architectural causes where evidence supports that conclusion; distinguish essential from accidental complexity, and candidate changes from pre-existing behavior. File length, number of findings and test count are indicators only.
5. For each mechanism classify: REQUIRED_CORE, REQUIRED_FOR_CLAIMED_PROFILE, OPTIONAL_DEFERABLE, LEGACY_RECONCILIATION, DUPLICATE_OR_UNNECESSARY, or INSUFFICIENT_EVIDENCE. Cite exact source paths/line ranges and requirement IDs. Establish reachable behavior before declaring a defect. Never treat missing proof as demonstrated defect.
6. Compare keep/current architecture, targeted simplification/decomposition, and a simpler coherent alternative where warranted. Evaluate user value, coupling, state/ownership proof, migration/regression cost, testability and operational burden. Preserve source freshness, scope, provenance, confidentiality, provider consent, independent roles, fail-closed behavior, exact completion and bounded resources; no guard deletion, second authority or parallel retrieval engine as a shortcut. Identify what can be removed only after equivalent evidence.
7. Propose a dependency-ordered delivery plan of small user-visible verticals: autonomous search; document extraction and attachment content retrieval; scoped lexical RAG; optional AI/graph/portability. Compare accelerating document retrieval with the existing Markdown-RAG-first roadmap without changing it. Separate recommendations requiring maintainer approval, security prerequisites, independently executable gates and deferred work.
8. Recommend KEEP_AND_COMPLETE, SIMPLIFY_BEFORE_CONTINUATION, or REPLACE_BOUNDED_CONTOUR for PR #155, with exact scope and reasons. No merge or approval of PR #155 follows from audit alone. If normative docs are pending review, give a separate concise DOCS_ONLY assessment only if independently qualified and complete; do not conflate audit and review.

## Report

Provide an evidence-based Russian report: executive conclusion; product boundary and principles compliance; actual architecture/component inventory; end-to-end product flows and acceptance status; requirements-to-mechanisms classification; complexity/root-cause assessment; security invariants; alternatives and trade-offs; PR #155 recommendation; proposed prioritized roadmap and bounded next contracts; decisions required from maintainer; validation limitations. Include exact pinned baseline/candidate, actual checks, findings with severity/traceability, and unknowns. Do not claim tests or runtime acceptance not performed. Keep public evidence sanitized; no automatic publication unless separately authorized.
